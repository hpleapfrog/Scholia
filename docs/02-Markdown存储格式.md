# Markdown 存储格式

> 状态：格式规范
> 上游：[抽象设计](00-抽象设计.md) · [GitHub 落地设计](01-GitHub落地设计.md)
> 一句话：**一切知识以 `.md` + front-matter 存储，GitHub 原生可读、可渲染、可 diff**

---

## 0. 为什么用 Markdown

| 好处 | 说明 |
|---|---|
| **人类可读** | 打开网页就能看懂，不需要任何工具 |
| **GitHub 原生渲染** | front-matter 之外的正文直接显示；**Mermaid 论证图会自动渲染** |
| **diff 可读** | PR 里看得见改了哪句话，而不只是哪个字段变了 |
| **AI 好读** | 大模型对 Markdown 的理解与生成都最稳 |
| **零工具依赖** | 不装任何东西也能贡献；将来加自动化不必改格式 |
| **可携带** | clone 下来就是完整可读的知识库，脱离平台照样能用 |

**代价**：结构松散、容易被写乱。所以必须靠**模板 + 文件级约束**压住（见 §2、§3）。

---

## 1. 文件级约束（三条硬规矩）

1. **一个知识点 = 一个文件。** 不合并、不拆散。这样 PR diff 干净、争议定位准、AI 抽取不会串味。
2. **front-matter 存机器需要的，正文存人需要的。** 同一个事实不写两处。
3. **正文段落顺序固定**：陈述 → 依据 → 论证 → 争议 → 适用范围 → 变更记录。顺序统一，机器才能可靠抽取。
   `## 论证` 小节**所有类型都必须存在**（草案下可为空并注明「尚无论证」）——结构统一才能可靠抽取。

## 2. 目录结构

```
knowledge/
├─ README.md                          # 总索引
└─ 物理/
   ├─ README.md                      # 学科索引 + 先修关系概览
   ├─ 命题/
   │  └─ 欧姆定律.md
   ├─ 教法/
   │  └─ 水管类比.md
   ├─ 误解/
   │  └─ 把电压当成水流速度.md
   ├─ 路径/
   │  └─ 初中电学12讲.md
   └─ 资源/
      └─ 水流动画.md
证据/
├─ README.md                          # 证据索引（表格）
└─ 导体U-I数据.csv                    # 可复算的原始数据
画像/
└─ 中考物理-零基础.md
投影/
└─ 中考物理-零基础-教科书.md
```

**按对象类型分目录**（命题 / 教法 / 误解 / 路径 / 资源），与抽象设计的四类对象一一对应。

### 命名与链接

- 文件名用**中文可读名**，因为它是给人看的
- 稳定标识放在 front-matter 的 `id` 字段里（`kb:physics:ohm-law`），因为中文文件名在 URL 里会被转义
- 内部链接用**相对路径 Markdown 链接**：`[电压](../命题/电压.md)`
- **不要用 `[[双链]]` 语法**——那是 Obsidian 的私有扩展，GitHub 不渲染

## 3. 通用 front-matter

字段名用英文（便于脚本与 AI 稳定解析），中文含义见下表。

```yaml
---
id: kb:physics:ohm-law          # 稳定标识，永不改变
type: 命题                       # 命题 | 教法 | 误解 | 路径 | 资源
title: 欧姆定律
status: 已确证                   # 取值见 §5
author: "@alice"                # 署名，不可匿名
created: 2026-09-10
updated: 2026-09-15
scope:                          # 适用范围（抽象设计公理 A1 的第三根支柱）
  学科: 物理
  学段: 初中
  适用: 全体
  条件: 温度恒定
edges:
  先修: ["[电流](../命题/电流.md)", "[电压](../命题/电压.md)", "[电阻](../命题/电阻.md)"]
  支持: []
  攻击: []
evidence: [ev-001, ev-002]      # 对应 证据/README.md 里的编号
license: CC-BY-SA-4.0
---
```

| 字段 | 含义 | 必填 |
|---|---|---|
| `id` | 稳定标识，重命名文件也不变 | ✅ |
| `type` | 五类对象之一 | ✅ |
| `title` | 人类可读标题 | ✅ |
| `status` | 状态，取值受 `type` 约束（§5） | ✅ |
| `author` | 最后一位实质性改动者 | ✅ |
| `created` / `updated` | 时间戳。**仅提示，不参与排序** | ✅ |
| `scope` | 适用范围。缺了它，任何结论都会被误用 | ✅ |
| `edges` | 先修 / 支持 / 攻击 | ✅ |
| `evidence` | 证据编号 | ✅ |
| `license` | 授权与再分发条款 | ✅ |

## 5. 状态取值（受 `type` 约束）

| `type` | 允许的 `status` |
|---|---|
| 命题 | 草案 · 待审 · 争议 · 暂定确认 · **已确证** · 已推翻 · 需复审 · 已失效 |
| 路径 | 草案 · 待审 · 有效 · 争议 · 需复审 · 已失效 |
| 教法 · 误解 · 资源 | 草案 · 待审 · 有效 · 争议 · 需复审 · 已失效 |

> [!IMPORTANT]
> **教法、误解、资源禁止使用「已确证」。**
> 它们是条件性的，不存在唯一正确。这条规则是抽象设计公理 A2「知识要收敛，教法要并存」在数据结构上的直接体现——**允许教法用「已确证」，就等于承认存在唯一最优教法**。

## 6. 状态由谁写（没有求值器时的诚实说明）

自动化求值器属于后续阶段。**在它上线之前，状态由 PR 评审人按规则人工判定并写入。**

规则不变，只是执行者暂时是人：

| 步骤 | 内容 |
|---|---|
| 1 | 列出所有论证，标出谁攻击谁 |
| 2 | 求存活集合：攻击者全部被击倒的论证才算存活 |
| 3 | 存活集合结论一致 → `已确证`；存在冲突 → `争议` |
| 4 | 把 `status` 与依据写进 PR 描述与「变更记录」表 |

**这样做仍然是可追溯、可重放的**：每一步都发生在 PR 里，git 历史完整保留。将来加上求值器，只是把这一步自动化，**格式一个字都不用改**。

> [!NOTE]
> 前提是**「变更记录」表必须每次都写**。它替代了自动求值器的审计输出，是这个阶段唯一的可追溯性来源。

## 7. GitHub 原生特性用法

### 争议标记

```markdown
> [!WARNING]
> **此处存在争议**：…
```

GitHub 支持的 alert 类型：`[!NOTE]` / `[!TIP]` / `[!IMPORTANT]` / `[!WARNING]` / `[!CAUTION]`。

| alert | 用途 |
|---|---|
| `[!WARNING]` | 存在争议 |
| `[!CAUTION]` | 禁忌、法律与安全风险、医疗免责 |
| `[!IMPORTANT]` | 规则性约束 |
| `[!NOTE]` | 补充说明 |

### 论证图

Mermaid 会被 GitHub 原生渲染，所以**论证图直接写在 `.md` 里就能看**：

````markdown
```mermaid
graph LR
  A1["A1 · 实验数据（存活）"] -->|支持| K["欧姆定律"]
  A2["A2 · 仅凭教材（被击倒）"] -->|支持| K
  A1 -.->|攻击：证据等级不足| A2
```
````

### 附件与证据

- 原始数据、脚本放进 `证据/` 目录，用相对链接引用
- **禁止上传教材原文或扫描页**（版权红线），只存页码定位与短引用

## 8. 与 01 文档的差异

| 原设计 | 现格式 | 原因 |
|---|---|---|
| `*.yaml` 对象文件 | `*.md` + front-matter | 可直接阅读与渲染，无需工具 |
| 独立 `arguments/` 目录 | 正文 `## 论证` 小节 | 减少文件数，论证与被论证对象同屏可读 |
| `derived` 字段由 CI 写入 | 「变更记录」表 + 人工按规则判定 | 本阶段不要工具链；格式不变，将来可自动化 |
| 论证图靠外部工具 | Mermaid 内嵌，GitHub 渲染 | 零依赖 |

**`evidence/` 索引、`guard-status` 护栏、PR 模板、分支保护**——这些在 01 文档里的设计**全部继续有效**，只是对象文件从 YAML 换成了 Markdown。
