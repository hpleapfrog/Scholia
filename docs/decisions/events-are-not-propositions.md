# 决策记录：`事件` 与 `命题` 分开

> **English: [events-are-not-propositions.en.md](events-are-not-propositions.en.md)**

**规则在 [FORMAT.md §4「`事件`」](../../FORMAT.md)**；本文件记的是**为什么**。

## 起因

一个真实需求：**记录正在发生的事件**（第一个是 2026 年 10 月伊尔库茨克反瘟疫研究所员工死亡事件），
并且**希望它能被持续维护、更新**。

我最初的做法是**把它塞进 `命题`**——理由是「本库已有的类型里，命题最接近」。

## 为什么塞进命题是错的

命题的核心结构是 `陈述` + `依据` + **`论证`** + `变更记录`，`status` 是
`已确证` / `已推翻` / `失据` 这一套——**它们全部围绕「一个可被攻击的陈述」转**。

而事件**没有可攻击的主张**。把「某机构在某日发布了某通报」写成命题：

- 它的 `论证` 段**没有攻击点**——「它确实发布了」不是靠论证成立的，是靠**日期与出处**；
- 它的 `status` 不知道该填什么——它既不会被「确证」，也不会被「推翻」；
- 结果是**一段没有攻击点的假论证**。**那正是本库要滤掉的噪音。**

更根本的问题：**命题回答「什么是真的」（有真值、可攻防、会收敛）；
事件回答「发生了什么」（时间索引的事实，只有证据）。两者是不同的东西。**

> [!IMPORTANT]
> **把事件写成命题，是为了套用已有的机器而制造出来的假结构。**
> 一旦同一份来源里既有「可攻防的主张」又有「发生过的事实」，
> 把它们压进同一种类型，就会让真的论证和假的结构混在一起，**读者分不出哪段是能攻击的**。

## 决定

**`事件` 不是第七种对象类型，而是与 `objects` 并列的另一类记录，单开顶层 `events/`。**

| 项 | `事件` | `命题`（对照） |
|---|---|---|
| 位置 | 顶层 `events/` | `knowledge/<学科>/命题/` |
| 回答 | 「发生了什么」 | 「什么是真的」 |
| `status` | `持续更新` / `已封存` | `已确证` / `已推翻` / `失据` … |
| 必备小节 | `陈述` · `依据` · `变更记录` | `陈述` · `依据` · **`论证`** · `变更记录` |
| 边 | **没有任何边** | `先修` / `支持` / `攻击` |
| `evidence` | **必须非空**（事件只需要证据） | 必须非空 |
| `index.json` | 单开 `事件[]` 一节，**不进 `objects`** | 进 `objects[]` |

**为什么单开顶层而不放进 `knowledge/<学科>/`**：事件常**跨学科**（鼠疫事件既是医学也是政治），
且它的组织维度是**时间**而不是学科。放进某个学科会迫使它选边，且脱离「按时间更新」的主线。

## 红线（用会失败的注入样本验证）

- 缺 `陈述` → 失败
- `evidence` 为空 → 失败
- `status` 用了命题的档（如 `已确证`）→ 失败
- 带了 `edges` → 失败
- `id` 前缀不是 `kb:event:` → 失败

样本在**临时副本**里验证，不污染仓库（见 [CONTRIBUTING「新规则入库门槛」](../../CONTRIBUTING.md)）。

## 必然的代价

1. **状态词表多了一套。** `持续更新` / `已封存` 与命题的档并排存在，
   读者要多记两个词——**换来的是「审核状态」与「事件状态」不再被混成一个字段**。
2. **`事件` 不进任何学科统计。** `knowledge/README.md` 的学科表末尾单列一行「事件（顶层）」，
   `对象总数` 仍只数知识对象。**两个数字并列，谁也不吞掉谁。**
3. **没有版本探测。** 事件靠人工按时间增补；本库仍无「来源改了就报警」的机制
   （这是已知缺口，不因本决策引入）。
