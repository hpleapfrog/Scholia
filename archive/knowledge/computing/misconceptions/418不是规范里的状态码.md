## 陈述

很多人把 **`418 I'm a teapot`** 当成 HTTP 的标准状态码之一，理由是「到处都能见到它」。
**它不是。**

两处规范都把它标为 **`(Unused)`**：

| 出处 | 怎么写 |
|---|---|
| **IANA 注册表**（2025-09-15） | `418` · Description = **`(Unused)`** · Reference = RFC 9110 §15.5.19 |
| **RFC 9110 §15.5.19** | 标题就是 **`418 (Unused)`**，正文说明它为什么被保留 |

RFC 9110 §15.5.19 的原文（短引用）：

> **[RFC2324] was an April 1 RFC** that lampooned the various ways HTTP was abused;
> one such abuse was the definition of an application-specific 418 status code,
> **which has been deployed as a joke often enough for the code to be unusable for any future use.**

拆开是三步：

1. **RFC 2324 是愚人节 RFC**（April 1 RFC），讽刺 HTTP 被滥用的各种方式
2. 其中一种讽刺就是**定义了一个应用专用的 418**
3. 这个玩笑**被部署得太多**，多到**这个码以后不能再被用于任何真实用途**

### 保留不是永久：4NN 耗尽时 418 可以再分配

同一节的后半段还写了三句，**转述里几乎见不到**（短引用）：

> Therefore, the 418 status code is **reserved** in the IANA HTTP Status Code Registry.
> This indicates that the status code **cannot be assigned to other applications currently**.
> **If future circumstances require its use (e.g., exhaustion of 4NN status codes), it can be
> re-assigned to another use.**

拆开是三点：

1. 418 被**保留**在 IANA 注册表里——所以它出现在注册表中，**不等于它是可用码**
2. 「当前」不能被分配给其他应用——**"currently" 是一个有时限的词**
3. **如果将来需要（例如 4NN 码段耗尽），它可以被重新分配给别的用途**

> [!IMPORTANT]
> **418 的状态是「当前保留」，不是「永久作废」。**
>
> **"cannot be assigned … currently" 与 "can be re-assigned" 是同一段话的两半**——
> 规范既说了它现在不能用，**也说了它将来可以被拿去干别的**。
>
> 于是「418 永远是茶壶」这个说法**在规范层面不成立**：
> **418 只是「现在没被用」，而且是在等一个将来可能到来的用途。**
> 这一点在本条目建立时（2026-10-12）没有记，2026-10-13 补上——
> **遗漏的正是这半段话。**

> [!IMPORTANT]
> **418 被保留，恰恰是因为它太流行。**
>
> 规范没有说「这个玩笑很无聊」，它说的是 **"deployed as a joke often enough for the code to be unusable"**——
> **玩笑的使用量本身把它烧掉了**。
>
> 所以「到处都能见到它」**不是它是标准码的证据，而是它是非标准码的原因**。
> 这个因果是反的，而这正是这条误解难以自我纠正的地方。

## 出现频率

> [!WARNING]
> **本条目暂无量化数据。**
>
> 本库**没有统计过**有多少文档、库或教程把 418 当成标准状态码。
> 「到处都能见到」是定性观察，**不是测量**。
>
> 目前唯一可核验的依据是**两处规范都把它标为 `(Unused)`**。
> 它证明「418 不是标准码」，**但证明不了「多少人误以为它是」**——
> **这两件事不是一回事，不能拿前者冒充后者。**

## 为什么值得记录

> [!WARNING]
> 这条误解**极难自我纠正**，原因是它自带一个看似合理的证据：
> **「我在很多地方都见过它」**。
>
> 而 RFC 9110 给出的因果正好相反——**见过得多，是因为被当成玩笑部署得多**。
>
> 更麻烦的是：**很多 HTTP 库确实会返回 418**（作为自嘲或占位），
> 于是「服务器真的返回了 418」这个观察**也不足以证明它是标准码**。
> 要证伪这条误解，**只能回到规范与注册表**，观察性证据在这里是失效的。

## 论证

### M1 · 两处规范一致标为 (Unused)（尚无攻击）

- **主张**：418 **不是**规范里的状态码，它是被保留的码
- **前提**：IANA 注册表 2025-09-15 版把 `418` 的 Description 写作 `(Unused)`，
  Reference 指向 RFC 9110 §15.5.19；该节标题即 `418 (Unused)`（ev-057, ev-054）
- **推理**：
  1. 这属于「**规范与官方文档规定了什么**」——正是[计算机](../README.md)学科收的东西
  2. 它**可被读者点开注册表与 RFC 逐字核对**
  3. **两个独立发布主体给出同一个结论**（IANA 与 IETF），
     且 IANA 的 Reference 直接指向 RFC 9110 对应小节，交叉可查
- **证据**：ev-054, ev-057
- **被攻击**：见 M2

### M2 · 本条不判断任何具体实现是否返回 418（尚无攻击）

- **主张**：本条声明的是「**418 不在规范里**」，
  **不声明「我的服务器不能返回 418」**
- **前提**：RFC 9110 自己说了，这个码 **"has been deployed as a joke often enough"**——
  也就是说，**大量部署确实存在**（ev-054）
- **推理**：
  1. 某个框架、某个 API 返回 418 **是事实**，本条不否认
  2. 但**「部署存在」与「规范定义」是两件事**：
     §15 前言明写状态码是可扩展的，未识别码按类别 `x00` 处理，
     所以一个返回 418 的服务**在协议层等价于返回 400**
  3. 因此本条**不能被用来支持「返回 418 的服务行为不合规」**——
     按 §15 前言，它的行为是**可解释的**
- **证据**：ev-054, ev-057
- **被攻击**：**本库没有核对任何具体库或框架是否返回 418。**
  「哪个库在什么情况下返回 418」——**这个问题本库一条都没查。**
  另外：**本库没有读 RFC 2324 原文**，只读了 RFC 9110 对它的转述。
  RFC 2324 全文里还写了什么、以及是否存在后续的愚人节 RFC，
  **本库一概不知道。**
- **署名**：@hpleapfrog · 2026-10-12
- **待补**：RFC 2324 原文；返回 418 的具体实现清单（需实测）
