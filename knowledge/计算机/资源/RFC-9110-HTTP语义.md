> [!IMPORTANT]
> **这份文档的结构本身是一条信息。**
>
> RFC 9110 把 **语义**（semantics）从 **报文语法**（HTTP/1.1 messaging syntax）
> 里拆了出来：`HTTP/1.1` 由 RFC 9110 + `HTTP Caching` + `HTTP/1.1`（报文语法）**三份文档共同定义**。
> 所以「HTTP/1.1 的规定」**不在任何单一 RFC 里**——这是读 HTTP 规范最常见的定位错误。

### 本库核过的四处

| 节 | 内容 | 定位 |
|---|---|---|
| §2.2 | 需求关键词引用条款 | "…interpreted as described in BCP 14 [RFC2119] [RFC8174] **when, and only when, they appear in all capitals**" |
| §9.2.1 | 安全方法 | "the `GET`, `HEAD`, `OPTIONS`, and `TRACE` methods are defined to be **safe**" |
| §9.2.2 | 幂等方法 | "`PUT`, `DELETE`, and **safe request methods** are idempotent" |
| §15 前言 | 状态码总则 | "The **first digit** … defines the class" / "**not required to understand … all registered status codes**" / "Values outside the range **100..599 are invalid**" |

## 用法

### 这份文本能支撑什么、不能支撑什么

| 能 | 不能 |
|---|---|
| 「**某个方法在规范里属于哪一类**」——安全 / 幂等 / 缓存，§9.2 有明文分类 | 「**实际服务器怎么实现**」——规范只规定语义，不规定实现 |
| 「**HTTP/1.1 由哪几份文档定义**」——§2.5 写明是三份的组合 | 「**HTTP/2、HTTP/3 的报文语法**」——分别在别的 RFC 里，本库未登记 |
| 「**不认识的状态码怎么处理**」——§15 前言有明文 | 「**`204` / `451` 这类具体码的定义**」——§15.2–§15.6 未逐条核 |
| 「**规范要求的关键词只在全大写时成立**」——§2.2 原文 | 「**某条要求的具体数值**」——本库只核了 §2.2 与 §9.2，其余未核 |

## 论证

### R3 · 为什么值得作为资源收进来（尚无攻击）

- **主张**：RFC 9110 值得进入本库的资源层
- **前提**：它是 IETF 的 STD 97（Internet Standard，**IETF 里最高的一档**），
  有编号、有发布日期、官方全文公开，本库核到三节原文（ev-054）
- **推理**：
  1. 它满足 `资源` 的门槛：**官方定位 + 可访问 + 章节可引用**
  2. 它是[计算机](../README.md)学科里「**协议规定了什么**」这一类的**主干来源**——
     HTTP 是本学科里被引用次数最多的协议，没有之一
  3. **「语义与语法分文档」这个结构本身就是稀缺信息**：
     网上几乎所有的「HTTP/1.1 规范」转述都把三份文档当成一份
- **证据**：ev-054
- **被攻击**：**本库只核了 10785 行里的四处**——§2.2、§9.2.1、§9.2.2，以及 §15 的前言。
  这意味着本条目**不能用来支撑任何关于 §15.2–§15.6 具体状态码、§13 条件请求、
  §8 表示元数据的具体主张**——那些内容本库一行都没核。
  §15 前言的总则可用，**但「`204` 为什么不能有正文」这类问题不在其中**。
  另外：**本库没有核 RFC 9110 之后是否有新的更新或勘误**，
  也没有查 RFC Editor 上这份文档的当前状态。
- **署名**：@hpleapfrog · 2026-10-12
- **待补**：§15.2–§15.6 状态码逐条核对；RFC 9110 的勘误表（errata）
