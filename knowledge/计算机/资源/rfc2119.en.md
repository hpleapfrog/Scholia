### What this document specifies

The **original definitions** of the five keywords (short quotes):

| Keyword | Equivalent | Definition (short quote) |
|---|---|---|
| `MUST` | `REQUIRED` / `SHALL` | "the definition is an **absolute requirement** of the specification" |
| `MUST NOT` | `SHALL NOT` | "the definition is an **absolute prohibition** of the specification" |
| `SHOULD` | `RECOMMENDED` | "there may exist valid reasons in particular circumstances to ignore a particular item, but **the full implications must be understood and carefully weighed**" |
| `SHOULD NOT` | `NOT RECOMMENDED` | "there may exist valid reasons in particular circumstances when the particular behavior is acceptable or even useful" |
| `MAY` | `OPTIONAL` | "an item is **truly optional**" |

> [!IMPORTANT]
> **RFC 2119 itself says nothing about capitalisation.**
>
> It says these words "are **often** capitalized" —
> and it does **not** say "only the capitals carry this meaning".
> That gap was closed by RFC 8174 in 2017 — see
> [RFC requirement keywords only hold in all capitals](../命题/rfc-keywords-require-uppercase.en.md).

## How to use

### What this text can and cannot support

| Can | Cannot |
|---|---|
| "**How strong is `MUST` in an RFC**" — five definitions, checkable one by one | "**Does a lowercase `must` count as a requirement**" — RFC 2119 does not answer; see RFC 8174 |
| "**`SHOULD` is not `SHOULD MUST`**" — deviation is allowed, but the full implications must be weighed first | "**Is this RFC itself the latest**" — it has been amended by RFC 8174 |
| "**Interoperability duties between implementations for `MAY`**" — §5 spells them out in both directions | "**Which word does a given RFC use**" — that requires reading that RFC |

> [!NOTE]
> RFC 2119 §6 also carries a **usage constraint** that is easy to overlook:
> these imperatives "**must be used with care and sparingly**", and
> "**MUST only be used where it is actually required for interoperation or to limit behavior
> which has potential for causing harm**".
> In other words: **the specification itself treats over-use of MUST as a defect.**

## Argument

### R3 · Why it is worth entering the resource layer (no attack yet)

- **Claim**: RFC 2119 deserves a place in this repo's resource layer
- **Premise**: it is an IETF BCP (Best Current Practice), with a number, a publication
  date and publicly accessible official text; this repo read it end to end (ev-052)
- **Reasoning**:
  1. it clears the bar for `资源`: **official locator + accessible + citable sections**
  2. it is the **precondition for reading almost any RFC** in the [computing](../README.en.md) subject —
     without knowing the strength of MUST, every RFC is misread
  3. "**one right answer, routinely taken for granted**" is exactly why this repo exists:
     online retellings almost always render SHOULD as "a suggestion you may ignore",
     dropping the second half about weighing the full implications
- **Evidence**: ev-052
- **Attacked**: **this repo cannot verify whether RFC 2119 will be updated again.**
  RFCs are immutable once published (they can only be obsoleted or updated by a later RFC),
  so "the 1997 text says so" is solid; but **whether this BCP 14 pairing is still the current
  version, this repo has not checked RFC Editor's current-status page**.
  Also: **this repo has not checked the history of these words in RFCs predating RFC 2119** —
  §6 says the definitions are "an amalgam of definitions taken from a number of RFCs",
  and this repo has read none of those earlier RFCs.
