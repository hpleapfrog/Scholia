## 定位

| 项 | 值 |
|---|---|
| 文件名 | **RFC 2119 · Key words for use in RFCs to Indicate Requirement Levels** |
| 发布组织 | IETF（Internet Engineering Task Force） |
| 分类 | **BCP 14 · Best Current Practice** |
| 发布日期 | **1997-03** |
| 作者 | Scott Bradner（Harvard University） |
| 结构 | 9 节；**核心是 §1–§5 的五条关键词定义** |
| 官方全文 | <https://www.rfc-editor.org/rfc/rfc2119.txt> |
| 核验深度 | **全文**——本库通读 §1–§7 |
| 状态 | **未被废止**，但被 **RFC 8174 修改**（见下） |

### 这份文本规定了什么

五条关键词的**定义原文**（短引用）：

| 关键词 | 等价词 | 定义（短引用） |
|---|---|---|
| `MUST` | `REQUIRED` / `SHALL` | "the definition is an **absolute requirement** of the specification" |
| `MUST NOT` | `SHALL NOT` | "the definition is an **absolute prohibition** of the specification" |
| `SHOULD` | `RECOMMENDED` | "there may exist valid reasons in particular circumstances to ignore a particular item, but **the full implications must be understood and carefully weighed**" |
| `SHOULD NOT` | `NOT RECOMMENDED` | "there may exist valid reasons in particular circumstances when the particular behavior is acceptable or even useful" |
| `MAY` | `OPTIONAL` | "an item is **truly optional**" |

> [!IMPORTANT]
> **RFC 2119 本身不规定「大小写」。**
>
> 它说的是这些词 "are **often** capitalized"（常常大写），
> 而**没有说「只有大写才有这个含义」**。
> 这个漏洞由 RFC 8174 在 2017 年补上——见
> [RFC 要求关键词只有全大写才成立](../命题/RFC要求关键词只有全大写才成立.md)。

### 许可与引用边界

> [!CAUTION]
> **本库不转载 RFC 的正文。**
>
> RFC 由 IETF Trust 持有版权（BCP 78）。**只存定位、章节编号与短引用**——
> 与教材、法律文本同样的处理：「不确定能不能转」的时候，
> **只引用**是唯一不需要判断的做法。

## 用法

### 这份文本能支撑什么、不能支撑什么

| 能 | 不能 |
|---|---|
| 「**RFC 里 MUST 是什么强度**」——五条定义逐条可查 | 「**小写 must 算不算要求**」——RFC 2119 没回答，要查 RFC 8174 |
| 「**SHOULD 不是 SHOULD MUST**」——它允许忽略，但要求先评估后果 | 「**这份 RFC 本身是不是最新的**」——它已被 RFC 8174 修改 |
| 「**MAY 的实现间互操作要求**」——§5 明文规定双向准备互通 | 「**某个具体 RFC 用了哪个词**」——那要查那份 RFC 自己 |

> [!NOTE]
> RFC 2119 §6 还给了一条常被忽略的**使用约束**：
> 这些祈使词 "**must be used with care and sparingly**"，
> "**MUST only be used where it is actually required for interoperation or to limit behavior which has potential for causing harm**"。
> 也就是说：**规范自己也认为滥用 MUST 是问题**。

## 论证

### R3 · 为什么值得作为资源收进来（尚无攻击）

- **主张**：RFC 2119 值得进入本库的资源层
- **前提**：它是 IETF 的 BCP（Best Current Practice），有编号、有发布日期、
  官方全文可公开访问，本库通读全文（ev-052）
- **推理**：
  1. 它满足 `资源` 的门槛：**官方定位 + 可访问 + 章节可引用**
  2. 它是[计算机](../README.md)学科里**几乎所有 RFC 阅读的前提**——
     不知道 MUST 的强度，读任何一份 RFC 都会读错
  3. **「有唯一正确答案、且答案常被想当然」正是本库存在的理由**：
     网上大量转述把 SHOULD 说成「建议，可不遵守」，
     漏掉了"必须先理解全部后果再 weighed"这半句
- **证据**：ev-052
- **被攻击**：**本库无法核实 RFC 2119 是否会被进一步更新。**
  RFC 一旦发布就不再修改（只能被新 RFC 废止或更新），
  所以「1997 年原文如此」是稳的；但 **BCP 14 这个组合是否仍是当前版本，
  本库没有查 RFC Editor 的当前状态页**。
  另外：**本库没有核对 RFC 2119 之前各 RFC 里这些词的用法史**，
  §6 说定义是 "an amalgam of definitions taken from a number of RFCs"，
  那些早期 RFC 本库一篇都没读。
- **署名**：@hpleapfrog · 2026-10-12
- **待补**：RFC Editor 的 BCP 14 当前状态页；RFC 2119 之前的关键词用法来源
