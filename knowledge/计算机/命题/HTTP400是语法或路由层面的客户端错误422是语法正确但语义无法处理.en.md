## Statement

**400 (Bad Request) is a client error at the syntax or routing level; 422 (Unprocessable Content) is correct syntax that cannot be processed semantically.**

RFC 9110 §15.5.1 states (short quote):

> The 400 (Bad Request) status code indicates that the server **cannot or will not
> process the request** due to something that is perceived to be **a client error**
> (e.g., **malformed request syntax**, **invalid request message framing**, or
> **deceptive request routing**).

RFC 9110 §15.5.21 states (short quote):

> The 422 (Unprocessable Content) status code indicates that the server
> **understands the content type of the request content** (hence a 415 (Unsupported Media
> Type) status code is inappropriate), and the **syntax of the request content is correct**,
> but it was **unable to process the contained instructions**. For example, this status code
> can be sent if an XML request content contains **well-formed (i.e., syntactically correct),
> but semantically erroneous** XML instructions.

### The criterion that divides them

| Code | Syntax | Semantics | Situations the specification lists |
|---|---|---|---|
| **400** | **broken** | — | `malformed request syntax` / `invalid request message framing` / `deceptive request routing` |
| **422** | **correct** | **unprocessable** | `well-formed but semantically erroneous` instructions |

**The specification supplies the exclusion itself**: 422's definition states "hence a 415 … is inappropriate" — **400, 415 and 422 are three different doors, not interchangeable synonyms.**

## Argument

### A1 · "Use 400 for any validation failure" merges three things into one at the specification level (not yet attacked)

- **Claim**: **the 400 / 422 division is "syntax/routing" versus "semantics"**; **a parameter-validation failure does not fall inside 400's three listed situations**
- **Premise**: §15.5.1 lists `malformed request syntax`, `invalid request message framing` and `deceptive request routing` — **all three are "the request was written wrong" or "the route is wrong"**; §15.5.21 states outright `syntax of the request content is correct` (ev-054)
- **Reasoning**:
  1. This is "what a standard or official document specifies" — exactly what the [computing](../README.en.md) discipline collects
  2. **"a JSON object is missing a field" / "age was sent as a string" is syntactically correct and semantically invalid** — by the specification's division **this falls inside 422's definition, not 400's three situations**
  3. The specification supplies a third door: **a wrong media type is 415** — §15.5.21 uses "hence a 415 … is inappropriate" **to exclude 415 on purpose**, showing **the specification itself lines these three codes up**
  4. Same shape as the [401 / 403 division](HTTP401必须带WWW-Authenticate头部且401与403的分工不是没登录对没权限.en.md): **retellings give a simple boundary; the specification gives a finer one**
- **Evidence**: ev-054
- **Attacked by**: see A2

### A2 · 422's original source is not RFC 9110, and this entry has not checked it (not yet attacked)

- **Claim**: this entry states **RFC 9110 §15.5.21's definition of 422**
- **Premise**: RFC 9110 §15.5.21 says only "what 422 means", **not where it came from** (ev-054)
- **Reasoning**:
  1. **422 was originally defined by WebDAV ([RFC 4918]), not by HTTP itself** — RFC 9110 renamed it when folding it into §15 (the old name was `Unprocessable Entity`), **but RFC 9110's body mentions neither the old name nor the old source**
  2. So this entry **cannot be used to claim "422 was an HTTP status code from the start"** — **it came from an extension specification and was later adopted**
  3. The same applies to `413`: RFC 9110 calls it `Content Too Large`, and the old name `Payload Too Large` is likewise absent from the body
- **Evidence**: ev-054
- **Attacked by**: **This entry states the text of RFC 9110 §15.5.1 and §15.5.21 only; it does not guarantee the behaviour of any specific API.** "Use 422 for validation failures" is **an inference from the specification's semantics, not a rule the specification states** — **the specification does not say "a parameter-validation failure should use 422"**. Also: **this entry has not checked [RFC 4918] (422's original source)**, nor **how older RFCs (7230–7235) worded 400**, nor **whether any mainstream API uses 400 or 422 in practice**.
- **Author**: @hpleapfrog · 2026-10-13
- **To be added**: [RFC 4918]; RFC 7230–7235's wording of 400; measured use of 400 versus 422 by mainstream APIs

## Why this counts as real information rather than noise

> [!IMPORTANT]
> **Any HTTP tutorial tells you "400 means a bad request"; none tells you the specification lists exactly three situations for 400 and that all three are syntax or routing, and none tells you the specification opened 422 separately for "correct syntax, wrong semantics".**
>
> The latter two are each a piece of the specification's wording, and almost never survive retelling:
> **"all three of 400's situations are about writing the request wrong" determines that a validation failure does not sit inside 400 in the specification's semantics;
> "422 states 415 is inappropriate" shows 400 / 415 / 422 are three doors the specification itself lines up, not interchangeable synonyms.**
>
> **This library's mission is to remove noise and store real information.**
> "400 means a bad request" is noise — tutorials all cover it.
> "400's three situations are syntax / framing / routing; 422 is correct syntax with wrong semantics; and 415 is explicitly excluded" — these sit inside the parentheses and examples of RFC 9110 §15.5.1 and §15.5.21, **and are what this library should hold**.
