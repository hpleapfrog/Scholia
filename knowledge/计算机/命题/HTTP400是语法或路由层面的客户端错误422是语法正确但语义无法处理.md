## 陈述

**400（Bad Request）是语法或路由层面的客户端错误；422（Unprocessable Content）是语法正确、但语义无法处理。**

RFC 9110 §15.5.1 原文（短引用）：

> The 400 (Bad Request) status code indicates that the server **cannot or will not
> process the request** due to something that is perceived to be **a client error**
> (e.g., **malformed request syntax**, **invalid request message framing**, or
> **deceptive request routing**).

RFC 9110 §15.5.21 原文（短引用）：

> The 422 (Unprocessable Content) status code indicates that the server
> **understands the content type of the request content** (hence a 415 (Unsupported Media
> Type) status code is inappropriate), and the **syntax of the request content is correct**,
> but it was **unable to process the contained instructions**. For example, this status code
> can be sent if an XML request content contains **well-formed (i.e., syntactically correct),
> but semantically erroneous** XML instructions.

### 分工的判据

| 码 | 语法 | 语义 | 规范列举的情形 |
|---|---|---|---|
| **400** | **坏了** | — | `malformed request syntax` / `invalid request message framing` / `deceptive request routing` |
| **422** | **正确** | **无法处理** | `well-formed but semantically erroneous` instructions |

**规范自己给了反向排除**：422 的定义明写「因此 415 不合适」——
**422 与 400 之间还夹着 415（媒体类型不支持），三者是三道不同的门。**

## 论证

### A1 · 「校验失败一律用 400」在规范层面是把三件事混成一件（尚无攻击）

- **主张**：**400 与 422 的分工是「语法/路由」对「语义」**，
  参数校验失败**不属于 400 的三种列举情形**
- **前提**：§15.5.1 列举的是 `malformed request syntax`、
  `invalid request message framing`、`deceptive request routing`——
  **三条都是「请求本身没写对」或「路由不对」**；
  §15.5.21 明写 `syntax of the request content is correct`（ev-054）
- **推理**：
  1. 这属于「**标准与官方文档规定了什么**」——正是[计算机](../README.md)学科收的东西
  2. **「JSON 里少个字段」「年龄填了字符串」是语法正确、语义不合法**——
     按规范的分工，**这落在 422 的定义里，不在 400 的三种情形里**
  3. 规范还给了第三道门：**媒体类型不对是 415**——
     §15.5.21 用 "hence a 415 … is inappropriate" **主动把 415 排除在外**，
     说明**这三个码是被规范自己摆成一排的**
  4. 与 [401/403 的分工](HTTP401必须带WWW-Authenticate头部且401与403的分工不是没登录对没权限.md)同型：
     **转述给了一个简单的分界，规范给的是另一条更细的**
- **证据**：ev-054
- **被攻击**：见 A2

### A2 · 422 的最初出处不在 RFC 9110，本条未核（尚无攻击）

- **主张**：本条陈述的是 **RFC 9110 §15.5.21 对 422 的定义**
- **前提**：RFC 9110 §15.5.21 只写了「422 表示什么」，
  **没有写它从哪来**（ev-054）
- **推理**：
  1. **422 最初由 WebDAV 定义（[RFC 4918]），不是 HTTP 本体规范**——
     RFC 9110 把它收进 §15 时改了名称（旧名 `Unprocessable Entity`），
     **但 RFC 9110 正文没有提及旧名或旧出处**
  2. 于是本条**不能被用来主张「422 从一开始就是 HTTP 状态码」**——
     **它来自一个扩展规范，后来才被收编**
  3. 同样的情况见于 `413`：RFC 9110 称其为 `Content Too Large`，
     旧名 `Payload Too Large` 同样未在正文提及
- **证据**：ev-054
- **被攻击**：**本条只陈述 RFC 9110 §15.5.1 与 §15.5.21 的原文，不保证任何具体 API 的用法。**
  「校验失败该用 422」是**规范语义的推论**，不是规范的规定——
  **规范没有说「参数校验失败应当用 422」**。
  另外：**本条未核对 [RFC 4918]（422 的最初出处）**，
  也**未核对旧版 RFC（7230–7235）对 400 的表述**，
  也**未核对任何主流 API 实际用 400 还是 422**。
- **署名**：@hpleapfrog · 2026-10-13
- **待补**：[RFC 4918]；RFC 7230–7235 对 400 的表述；主流 API 用 400 还是 422 的实测

## 为什么这条算「真实信息」而不是「噪音」

> [!IMPORTANT]
> **任何一篇 HTTP 教程都会告诉你「400 表示请求错误」，但不会告诉你规范把 400 的情形列成三条且全是语法或路由问题，也不会告诉你规范为「语法正确但语义错误」单独开了 422。**
>
> 后两条都是规范里的措辞，转述里几乎见不到：
> **「400 的三种情形都是没写对」决定了参数校验失败在规范语义里不属于 400；
> 「422 明写 415 不合适」则说明 400 / 415 / 422 是规范自己摆成一排的三道门，不是可以互换的同义词。**
>
> **本库的使命是「去除噪音、存放真实信息」。**
> 「400 表示请求错误」是噪音——教程都在讲；
> 「400 的三种情形是语法/组帧/路由、422 是语法正确语义错误、且 415 被主动排除」——
> 这几条藏在 RFC 9110 §15.5.1 与 §15.5.21 的括号与例句里，**才是本库该装的。**
