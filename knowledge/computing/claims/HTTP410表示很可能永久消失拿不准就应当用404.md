## 陈述

**410（Gone）表示目标资源在源服务器上已不可用，且该状态「很可能永久」。**
**如果源服务器不知道、或无从判断是否永久，规范要求改用 404（Not Found）。**

RFC 9110 §15.5.11 原文（短引用）：

> The 410 (Gone) status code indicates that access to the target resource is **no longer
> available** at the origin server and that this condition is **likely to be permanent**.
> **If the origin server does not know, or has no facility to determine, whether or not the
> condition is permanent, the status code 404 (Not Found) ought to be used instead.**

### 410 的设计用途：让外链被删掉

同节写明了 410 主要是给谁看的（短引用）：

> The 410 response is primarily intended to **assist the task of web maintenance**
> by notifying the recipient that the resource is **intentionally unavailable** and that
> the server owners **desire that remote links to that resource be removed**.

规范还补了一句边界（短引用）：

> It is **not necessary** to mark all permanently unavailable resources as "gone"
> or to keep the mark for any length of time — that is left to the discretion of the server owner.

### 缓存

§15.5.11 末段：

> A 410 response is **heuristically cacheable**; i.e., unless otherwise indicated
> by the method definition or explicit cache controls.

## 论证

### A1 · 410 与 404 的分工是「是否永久」，不是「资源在不在」（尚无攻击）

- **主张**：410 与 404 的区别**不在「资源找不找得到」，而在「消失得永不永久」**；
  **拿不准是否永久时，规范要求用 404**
- **前提**：§15.5.11 明写 "likely to be permanent" 与
  "does not know … **ought to be used instead**"（ev-054）
- **推理**：
  1. 这属于「**标准与官方文档规定了什么**」——正是[计算机](../README.md)学科收的东西
  2. 常见误解是「410 = 更强的 404」——**规范说的不是强度，是置信度**：
     410 是「我知道它没了，而且大概永远没了」，
     404 是「我不知道它在不在，或者它没了但我不确定还会不会回来」
  3. 于是**用 410 是一个承诺**：你对外宣称这个资源是**故意**下线的，
     并且希望外链被删——**这是给网页维护者发的信号，不是给最终用户的**
- **证据**：ev-054
- **被攻击**：见 A2

### A2 · 「很可能永久」是规范语气，不是硬性判据（尚无攻击）

- **主张**：本条陈述的是**规范怎么区分 410 与 404**，
  **不提供「怎样才算永久」的可操作判据**
- **前提**：§15.5.11 用的是 "**likely** to be permanent" 与 "ought to be used"
  （ev-054）
- **推理**：
  1. "**很可能**永久"是规范自己的措辞——**规范没有定义「很可能」的门槛**，
     也没有规定「下线多久算永久」
  2. 规范同节还说：**不必**把所有永久不可用的资源都标成 gone，
     标多久也**由服务器所有者自行决定**——**规范把裁量权交了出去**
  3. 所以本条**不能被用来主张「下线超过 N 天就必须返回 410」**
  4. 与 [204 默认可缓存](HTTP204响应不能含正文也不能含trailer且默认可缓存.md)、
     [405 必须带 Allow](HTTP405响应必须带Allow头部且默认可缓存.md) 一样，
     **「heuristically cacheable」是规范的默认值，不是实现的义务**
- **证据**：ev-054
- **被攻击**：**本条只陈述 RFC 9110 §15.5.11 的原文，不保证任何具体服务端的行为。**
  「很可能永久」没有门槛，「不必标记所有」是规范明说的裁量。
  另外：**本条未核对旧版 RFC（7230–7235）对 410 的表述**。
- **署名**：@hpleapfrog · 2026-10-13
- **待补**：RFC 7230–7235 对 410 的表述；主流服务端使用 410 的实测

## 为什么这条算「真实信息」而不是「噪音」

> [!IMPORTANT]
> **任何一篇 HTTP 教程都会告诉你「410 表示资源已删除」，但不会告诉你规范要求「拿不准是否永久就改用 404」。**
>
> 后者是规范里的一句话，转述里几乎见不到：
> **它决定了一个 410 是不是一个承诺——你对外宣称这个资源是故意下线的，并且希望外链被删。**
>
> **本库的使命是「去除噪音、存放真实信息」。**
> 「410 表示资源已删除」是噪音——教程都在讲；
> 「410 表示很可能永久消失，拿不准就用 404，且 410 是发给网页维护者的信号」——
> 这几条藏在 RFC 9110 §15.5.11 的几句长句里，**才是本库该装的。**
