## 陈述

**402 在规范里只有一句「保留待用」；305 在上一个版本里被废弃；306 不再使用、码位保留。三个码都还在注册表里，但规范没有给其中任何一个定义可依循的行为。**

RFC 9110 §15.5.3 全文即一句话（短引用）：

> The 402 (Payment Required) status code is **reserved for future use**.

§15.4.6（短引用）：

> The 305 (Use Proxy) status code was defined in a previous version of
> this specification and is **now deprecated** (Appendix B of [RFC7231]).

§15.4.7（短引用）：

> The 306 status code was defined in a previous version of this
> specification, **is no longer used, and the code is reserved**.

### 「注册表里在册」不等于「规范里有语义」

三码都仍占着注册表的条目（306 在注册表里标为 (Unused)，见
[IANA 条目](HTTP状态码的完整清单在IANA注册表不在RFC9110里.md)），
但上面三段引文就是 RFC 9110 对它们的**全部**表述——
五节/四节/一节之外的任何「402 用来收钱」「305 该怎么绕代理」的说法，
都不在这份规范里。

## 论证

### A1 · 三个码的共同点是「占位」而非「功能」（尚无攻击）

- **主张**：402 / 305 / 306 的规范表述分别是「保留待用 / 已废弃 / 不再使用且保留」——
  三者都**没有定义任何可实现的语义**，与 404、410 那种「有明确行为规定」的码不同
- **前提**：§15.5.3、§15.4.6、§15.4.7 的引文即全部正文（ev-054）
- **推理**：
  1. 这属于「**标准与官方文档规定了什么**」——正是[计算机](../README.md)学科收的东西；
     而「402 表示要付款」「306 是代理切换」这类转述，规范里**查无出处**
  2. 注册与语义是两回事：注册表的「在册」只说明码位归属，
     **新语义要按注册流程进来**（见
     [新增状态码须过 IETF Review](新增HTTP状态码须过IETFReview且不能禁止正文.md)）——
     在那之前，402 就只是「保留」
  3. 这也是注册表治理的方式：**保留而非删除**，给未来留位
- **证据**：ev-054
- **被攻击**：见 A2

### A2 · 本条不预测 402 的未来，也不核对 305 的旧语义（尚无攻击）

- **主张**：本条只陈述 RFC 9110 现版对三码的表述，
  **不陈述「402 将来会不会被启用」「旧版 305 的完整规则」**
- **前提**：§15.4.6 把 305 的旧语义指向 `Appendix B of [RFC7231]`——**该附录本库未核**（ev-054）
- **推理**：
  1. 402 是否启用取决于后续规范与注册流程，本条无法预告
  2. 所以本条**不能被用来主张「以后收到 402 是正常的」或「旧版 305 就是这么用的」**
- **证据**：ev-054
- **被攻击**：**本条只陈述 RFC 9110 §15.5.3、§15.4.6、§15.4.7 的原文，不保证任何实现行为，也不预测注册表变化。**
- **署名**：@hpleapfrog · 2026-10-18
- **待补**：RFC 7231 Appendix B（305 旧语义）的核读；402 的启用状态（以注册表最新版为准）

## 为什么这条算「真实信息」而不是「噪音」

> [!IMPORTANT]
> **「402 是付款」「305 是代理」之类的解释满天飞；翻开规范会发现三段正文短得近乎空白。**
>
> 记住「它们都有注册、都没有语义」比记住任何转述都稳——
> **规范怎么定，看引文；引文就这几句。**
